# AI-Powered Adaptive Training Coach: Data Storage Choices (MVP)

This document outlines the data storage technology choices for the Minimum Viable Product (MVP) of the AI-Powered Adaptive Training Coach. The choices prioritize reliability, ease of use for common relational data, and foundational capabilities for future AI features.

## 1. Primary Database

*   **Choice:** PostgreSQL
*   **Version:** Latest stable version (e.g., PostgreSQL 15 or 16 at the time of development).

*   **Justification for MVP:**
    *   **Relational Integrity:** The core data (users, courses, modules, lessons, enrollments, progress, quiz attempts) is highly relational and benefits from ACID properties, strong consistency, and well-defined schemas. PostgreSQL excels in this.
    *   **Mature & Robust:** PostgreSQL is a highly reliable, feature-rich, and battle-tested open-source relational database system.
    *   **Extensibility:** Offers advanced data types (JSONB for flexible fields like quiz answers or content data, arrays), full-text search capabilities (can be used for basic keyword search in course descriptions if Elasticsearch is not part of MVP), and geospatial data support (if needed in the future).
    *   **Scalability:** While not as horizontally scalable out-of-the-box as some NoSQL databases for massive write loads, PostgreSQL can handle significant read/write traffic suitable for an MVP and can be scaled vertically or with read replicas. More advanced scaling solutions (e.g., Citus, sharding) are available for post-MVP if needed.
    *   **Community & Ecosystem:** Strong community support, extensive documentation, and compatibility with a wide range of ORMs (Object-Relational Mappers) and development tools.
    *   **Cost-Effective:** Open-source, reducing licensing costs. Managed PostgreSQL services are available on all major cloud providers (AWS RDS, Google Cloud SQL, Azure Database for PostgreSQL), simplifying administration.
    *   **JSONB for Flexibility:** For fields like `ContentData` in lessons or `Options` in questions, JSONB allows for schema flexibility within a relational structure, which is useful for varied content types without needing separate tables for each.

*   **Schema Reference:** The data schema will be based on the `AI_Adaptive_Training_Coach_Data_Schema.md` document, adapted for PostgreSQL syntax and specific MVP requirements.

## 2. Vector Database / Embeddings Storage

*   **Choice for MVP:** Not a dedicated vector database. Embeddings and TF-IDF vectors will be managed within the application layer or stored in a suitable format within PostgreSQL if dataset size is small to moderate.
    *   For TF-IDF vectors generated by the Personalization Engine, these are typically sparse and can be stored efficiently if needed, or recomputed. Given the MVP's scope (moderate number of courses), recomputing similarities on demand or caching them might be feasible without persistent vector storage.
    *   If pre-computed item embeddings (e.g., from a simple Word2Vec model on course descriptions) were to be used for recommendations, they could potentially be stored in a PostgreSQL table with an array or JSONB column for smaller dimensions, or a specialized extension.

*   **Justification for MVP:**
    *   **Simplicity:** Avoids introducing another database system for the MVP when the scale of vector data is likely manageable.
    *   **Cost:** Reduces infrastructure complexity and operational overhead.
    *   **TF-IDF Focus:** The MVP Personalization Engine relies on TF-IDF, where vectors are often computed on-the-fly or the document-term matrix itself is the primary artifact.

*   **Post-MVP Consideration:**
    *   As the number of courses and users grows, and if more sophisticated embedding-based recommendation models (e.g., Sentence-BERT, Universal Sentence Encoder) are implemented, a dedicated vector database (e.g., Pinecone, Weaviate, Milvus) or a PostgreSQL extension like `pgvector` will be evaluated. These systems are optimized for efficient similarity search in high-dimensional vector spaces.

## 3. Caching Solution

*   **Choice:** Redis
*   **Version:** Latest stable version.

*   **Justification for MVP:**
    *   **Performance:** Redis is an in-memory data store known for extremely fast read and write operations, significantly reducing latency for frequently accessed data.
    *   **Versatility:** Can be used for various caching patterns:
        *   **API Response Caching:** Caching responses for frequently requested, relatively static data (e.g., course details, popular lesson content).
        *   **Session Management:** Storing user session information.
        *   **Rate Limiting:** Tracking request counts for API rate limiting.
        *   **Leaderboards/Counters (Future):** If gamification elements are added.
        *   **Caching Personalization Results:** Storing top N recommendations for users for a short period to avoid recomputing on every request.
    *   **Ease of Use:** Simple key-value store semantics, with support for various data structures (strings, hashes, lists, sets, sorted sets).
    *   **Scalability & Resilience:** Can be clustered for scalability and high availability.
    *   **Ecosystem & Cloud Support:** Widely adopted, with excellent client libraries in most programming languages and managed services available on all major cloud platforms (AWS ElastiCache, Google Cloud Memorystore, Azure Cache for Redis).

## Summary of Rationale

The MVP data storage strategy prioritizes a strong relational foundation with PostgreSQL for core data integrity and complex queries. It defers the introduction of a specialized vector database to post-MVP stages to maintain simplicity and reduce initial overhead, while acknowledging its potential future need. Redis is included for its significant performance benefits through caching, which is crucial for a responsive user experience even at the MVP stage.
